# Планирование отпусков

Веб-приложение для планирования отпусков сотрудников отдела: список
сотрудников, таблица отпусков с автоматическим пересчётом дат/дней и
годовой календарь с подсветкой пересечений отпусков сотрудников,
занятых на одном проекте.

Реализовано строго по техническому заданию:

- **Список сотрудников** — создание/редактирование/удаление, диалог
  подтверждения при удалении, форма ввода имени, даты устройства (с
  расчётом общего стажа), списка проектов и цвета для календаря.
- **Таблица отпусков** — дата начала, дата окончания и количество дней;
  заполнение любых 2 из 3 полей рассчитывает третье; при ручном
  изменении дат пересчитывается количество дней, при ручном изменении
  количества дней — пересчитывается дата окончания. Пересечение с уже
  существующим отпуском того же сотрудника — отклоняется.
- **Календарь** — всегда весь текущий год (12 мини-календарей месяцев),
  цветные блоки с фамилиями сотрудников по дням, дополнительная
  подсветка дней-конфликтов (два сотрудника одного проекта в отпуске
  одновременно).
- **Роли** — менеджер видит и редактирует всех; обычный сотрудник
  видит календарь целиком (нужно для конфликтов), но может
  редактировать только свои отпуска и не может управлять списком
  сотрудников. Роль приходит из Keycloak.
- **Экспорт в CSV** — выгрузка отпусков за год (кнопка в календаре,
  только для менеджеров), открывается в Excel.
- **Напоминания об отпуске** — фоновая служба раз в сутки проверяет,
  у кого отпуск начинается через N дней, и отправляет email (если
  настроен SMTP); плюс колокольчик с ближайшими отпусками прямо в
  интерфейсе — работает без всякой настройки почты.
- **Стек**: фронтенд — TypeScript + React + Ant Design; бэкенд —
  ASP.NET Core (C#) + EF Core + PostgreSQL; авторизация — OpenID
  Connect (Keycloak).

## Важно — прочитать перед запуском

Код написан и вычитан вручную в среде без доступа в интернет и без
установленных .NET SDK / npm-пакетов, поэтому **не был скомпилирован и
не запускался** в процессе создания — это касается и самого
приложения, и тестов (`dotnet test` / `npm test` ни разу не
выполнялись). Архитектура и бизнес-логика проверены на бумаге и должны
быть верны, но при первом запуске возможны мелкие опечатки/несовпадения
версий пакетов — обычная история для сгенерированного кода. Первым
делом стоит просто попробовать `dotnet run`, `npm run dev` и
`dotnet test`/`npm test`, и поправить то, на что укажет компилятор.

## Быстрая проверка без Keycloak

Если Keycloak ещё не настроен (например, не работает Docker), можно
временно проверить весь остальной функционал — список сотрудников,
таблицу отпусков, календарь — без реальной авторизации:

- **Backend**: в `appsettings.Development.json` уже стоит
  `"Auth": { "Disabled": true }` — при обычном `dotnet run` (окружение
  Development по умолчанию) авторизация уже отключена "из коробки".
- **Frontend**: откройте `frontend/.env` и поставьте
  `VITE_AUTH_DISABLED=true`, затем перезапустите `npm run dev`.

С этими флагами приложение открывается сразу, без экрана входа, и все
запросы к API проходят без токена.

> **Это временный режим только для локальной разработки.** Перед
> показом/сдачей с настоящей авторизацией не забудьте вернуть оба
> флага в `false` (или удалить `Auth:Disabled` из
> `appsettings.Development.json`) и настроить Keycloak, как описано
> ниже.

> **О файле `appsettings.Development.json`:** он намеренно НЕ
> закоммичен в git (`.gitignore`) — это личный локальный конфиг
> (особенно важно, если туда позже впишете реальный пароль от SMTP,
> см. раздел "Напоминания об отпуске" ниже — такой пароль не должен
> попасть в публичный репозиторий). После клонирования репозитория
> создайте этот файл сами рядом с `appsettings.json`, с содержимым:
> ```json
> {
>   "Auth": { "Disabled": true },
>   "Logging": {
>     "LogLevel": {
>       "Default": "Information",
>       "Microsoft.AspNetCore": "Warning",
>       "Microsoft.EntityFrameworkCore": "Information"
>     }
>   }
> }
> ```

## Backend — запуск

Требования: .NET SDK 8.0+, PostgreSQL (поднимается через
`docker-compose.yml`, см. ниже).

```bash
docker compose up -d   # поднимет БД приложения (порт 5432) и Keycloak

cd backend/VacationPlanner.Api
dotnet restore
dotnet run
```

API поднимется на `http://localhost:5000`, Swagger UI — на
`http://localhost:5000/swagger`. База — PostgreSQL (`db` в
docker-compose, БД `vacationplanner`); строка подключения — в
`appsettings.json` → `ConnectionStrings:Default`. Схема БД создаётся
автоматически при первом запуске (`Database.EnsureCreated()` в
`Program.cs`).

> Схема БД по умолчанию создаётся через `EnsureCreated()` — просто и
> без лишних шагов. Для полноценных EF Core Migrations — см. раздел
> "EF Core Migrations" ниже, там же про переключатель
> `Database:UseMigrations`.

## Frontend — запуск

Требования: Node.js 20+.

```bash
cd frontend

```

## Настройка Keycloak

(если ещё не запускали — `docker compose up -d`, см. раздел про backend)

Откройте `http://localhost:8080`, войдите как `admin` / `admin`, затем:

1. **Realm** — создайте realm `vacation-planner`.
2. **Клиент фронтенда** (`vacation-planner-frontend`):
   - Client authentication: `Off` (public client, вход по коду с PKCE).
   - Standard flow: включён.
   - Valid redirect URIs: `http://localhost:5173/*`.
   - Web origins: `http://localhost:5173`.
3. **Клиент/аудитория бэкенда** (`vacation-planner-api`):
   - Проще всего добавить **audience mapper** на клиенте фронтенда
     (Client scopes → dedicated scope → Add mapper → Audience),
     указывающий `vacation-planner-api`, чтобы access-токен фронтенда
     содержал нужный `aud` и совпадал с `Auth:Audience` в
     `appsettings.json` бэкенда.
4. Создайте тестового пользователя (Users → Add user, затем вкладка
   Credentials → задать пароль, выключить "Temporary").
5. **Роль менеджера** (для доступа "видит и редактирует всех"):
   - Realm roles → Create role → имя `manager` → Save.
   - Users → выбранный пользователь → Role mapping → Assign role →
     отметить `manager` → Assign.
   - Роли попадают в токен автоматически (стандартный client scope
     `roles`, отдельно настраивать не нужно) — бэкенд сам разбирает
     `realm_access.roles` из токена (см. `Program.cs`).
6. **Связать сотрудника с логином** (чтобы обычный, не-менеджерский
   пользователь видел/редактировал именно себя): Users → выбранный
   пользователь → скопировать поле **ID** вверху страницы (это UUID) →
   вставить в форму сотрудника в приложении, поле "Keycloak user ID".
   Без этой связи обычный пользователь (без роли `manager`) не увидит
   ни одного своего отпуска — GetMyEmployeeIdAsync не найдёт совпадения.

Адреса и client_id вынесены в конфигурацию:
- Backend: `backend/VacationPlanner.Api/appsettings.json` → `Auth:Authority`, `Auth:Audience`.
- Frontend: `frontend/.env` → `VITE_OIDC_AUTHORITY`, `VITE_OIDC_CLIENT_ID`.

## Напоминания об отпуске (email)

Работает "из коробки" без настройки — если `Smtp:Host` пуст (значение
по умолчанию), письма не отправляются, а только логируются в консоль
backend. Чтобы включить настоящую отправку, заполните в
`appsettings.json` (или лучше — в `appsettings.Development.json`
локально, чтобы не хранить пароли в общем файле):

```json
"Smtp": {
  "Host": "smtp.gmail.com",
  "Port": 587,
  "Username": "you@gmail.com",
  "Password": "пароль приложения, не обычный пароль от почты",
  "From": "you@gmail.com",
  "EnableSsl": true
},
"Notifications": {
  "ReminderDaysBefore": 3,
  "CheckIntervalHours": 24
}
```

Для Gmail нужен именно **пароль приложения** (App password), обычный
пароль от аккаунта не подойдёт — Google требует включить
двухфакторную аутентификацию и создать отдельный пароль для приложений
в настройках аккаунта. Письмо отправляется сотруднику, у которого
заполнено поле Email и отпуск начинается ровно через
`ReminderDaysBefore` дней. Колокольчик с ближайшими отпусками в шапке
приложения работает независимо от SMTP — это отдельный, всегда
рабочий канал.

## EF Core Migrations

По умолчанию используется `EnsureCreated()` (просто, без лишних шагов).
Чтобы перейти на полноценные миграции:

```bash
cd backend/VacationPlanner.Api
dotnet tool install --global dotnet-ef   # если ещё не установлен
dotnet ef migrations add InitialCreate
```

> **Если в базе уже есть таблицы** (созданные через `EnsureCreated()` в
> прошлый раз) — переход на миграции проще всего сделать на чистой
> базе: удалите БД `vacationplanner` в pgAdmin и создайте заново
> (данные — тестовые, не жалко). Накатывать миграции поверх уже
> существующих вручную-созданных таблиц — отдельная и не самая
> приятная задача (пришлось бы вручную помечать миграцию как
> "уже применена").

Затем включите флаг в `appsettings.json` (или `appsettings.Development.json`):

```json
"Database": {
  "UseMigrations": true
}
```

При следующем `dotnet run` `Program.cs` вызовет `db.Database.Migrate()`
вместо `EnsureCreated()` и применит миграции автоматически.

## Обработка ошибок

Ошибки валидации (400) и необработанные исключения (500) возвращаются
в едином формате — [RFC 9457 ProblemDetails](https://www.rfc-editor.org/rfc/rfc9457)
(`application/problem+json`), с `traceId` для сопоставления с логами
сервера. В Development-окружении вместо этого показывается подробная
страница с деталями исключения (удобнее при отладке) — переключение в
`Program.cs`.

## CI/CD

`.github/workflows/ci.yml` — на каждый push/pull request в `main`
собирает backend (`dotnet build`) и frontend (`npm run build`),
прогоняет тесты обеих частей. Ничего никуда не деплоит — только
проверяет, что код собирается и тесты зелёные.

> `npm ci` в workflow требует закоммиченный `package-lock.json` — он
> появится сам после первого `npm install` у вас локально, не забудьте
> его закоммитить (обычно `.gitignore` его не исключает, только
> `node_modules/`).

## Docker — весь стек одной командой

```bash
docker compose up -d --build
```

Поднимет: PostgreSQL, Keycloak (+ его БД), backend (порт 5000),
frontend (порт 5173, собранная статика через nginx). Приложение —
`http://localhost:5173`.

> **Важно:** в этом сценарии backend и frontend запускаются с
> **отключённой авторизацией** (`Auth:Disabled` / `VITE_AUTH_DISABLED`
> прописаны прямо в `docker-compose.yml`). Это осознанный выбор —
> синхронизация того, как Keycloak виден из браузера (`localhost:8080`)
> и как он виден изнутри контейнера backend'а (другой сетевой путь) —
> отдельная, не всегда тривиальная задача сама по себе, и решать её
> ради демо-контейнеризации избыточно. Для проверки настоящей
> авторизации через Keycloak — используйте локальный workflow
> (`dotnet run` + `npm run dev`), описанный выше: там и backend, и
> браузер видят Keycloak одинаково, через `localhost:8080`.

## Ключевые архитектурные решения

- **Даты отпуска — источник истины, количество дней — производное.**
  Бэкенд хранит только `StartDate`/`EndDate`; `Days` вычисляется на
  лету (`EndDate - StartDate + 1`). Хитрая логика "какое поле только
  что редактировали" (см. ТЗ) — фронтенд-специфичный UX, поэтому она
  реализована в `frontend/src/utils/dateMath.ts` (`recalcVacation`), а
  на сервер всегда уходят уже согласованные даты начала/окончания.
- **Проекты создаются "по требованию".** Отдельного экрана управления
  проектами по ТЗ не предусмотрено — при вводе нового имени в поле
  "Проекты" сервер сам заводит запись в таблице `Projects`
  (`EmployeesController.SyncProjectsAsync`).
- **Конфликты считаются на фронтенде** (`utils/calendarIndex.ts`) по
  уже загрученным сотрудникам и отпускам: для каждого дня года
  собираются все активные отпуска, и если у двух разных сотрудников
  есть общий проект — оба помечаются как конфликтующие в этот день.
  Это даёт мгновенный отклик календаря без лишних запросов к API.
- **Таблица отпусков привязана к выбранному в списке сотруднику** —
  это соответствует раскладке макета (сотрудники → их отпуска →
  календарь всех).
- **Роль хранится в Keycloak, не в БД.** Бэкенд разбирает
  `realm_access.roles` из JWT-токена в `Program.cs`
  (`OnTokenValidated`) и добавляет как обычные ASP.NET Core
  Role-клеймы — дальше работают стандартные `[Authorize(Policy =
  "Manager")]` / `User.IsInRole(...)`. Логика "кто я" вынесена в
  `ICurrentUserContext` (`Services/CurrentUserContext.cs`), чтобы не
  дублировать её в каждом контроллере.
- **Видимость vs редактирование — разные правила.** `GET` для
  сотрудников и отпусков открыт всем авторизованным (иначе календарь
  не сможет показывать конфликты между коллегами). Ограничения по
  роли применяются только к записи (`POST`/`PUT`/`DELETE`) —
  `VacationsController` проверяет владельца через связь по
  `KeycloakUserId`, `EmployeesController` целиком закрыт политикой
  `Manager`. При `Auth:Disabled=true` пользователь всегда считается
  менеджером — чтобы локальная разработка без Keycloak не спотыкалась
  о ролевые ограничения.
- **Email-напоминания — через System.Net.Mail**, без дополнительных
  NuGet-пакетов; если SMTP не настроен — просто пишет в лог, не падает.

## Возможные доработки

- Самостоятельная привязка аккаунта ("claim my profile") вместо
  ручного копирования Keycloak user ID менеджером.
- Отдельный экран управления проектами (переименование/удаление).
- Экспорт в настоящий `.xlsx` (например, через ClosedXML) — сейчас
  экспорт в CSV, который открывается в Excel, но не даёт форматирования.
- Деплой в облако (Render/Railway/Vercel) — постоянная ссылка вместо
  локального запуска.
- Синхронизировать Keycloak между контейнером backend'а и браузером в
  `docker-compose.yml` (см. предупреждение в разделе "Docker" выше) —
  тогда полный стек можно будет поднимать с настоящей авторизацией.
